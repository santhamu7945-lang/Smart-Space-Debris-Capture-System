05B · CAPTURE COORDINATE BRIDGE

Orbital state becomes a physical arm command.

The orbital prediction is not sent directly to the robotic arm. A local capture coordinate is generated first, then inverse kinematics produces joint angles for the prototype workspace.

01 PREDICTION ECI / relative orbital state
→
02 LOCAL FRAME scaled capture XYZ
→
03 IK SOLVER joint-angle solution
→
04 SERIAL USB command packet
→
05 ARDUINO servo command interface
→
06 PCA9685 I²C PWM driver
→
07 ARM prototype actuation

PROTOTYPE WORKSPACE

Example local workspace: X = 0–30 cm, Y = −20–20 cm, Z = 0–25 cm. These are scaled laboratory coordinates and are not orbital distances.

JOINT COMMAND MODEL

Python performs the inverse-kinematics calculation. The Arduino receives joint commands rather than orbital XYZ coordinates. Example packet: JOINTS,111,74,102,68.

HARDWARE STATUS

Browser-side hardware connection is not claimed here. Arduino, PCA9685 and servos are represented as an external prototype integration layer unless a real serial connection is explicitly established.

07 · DECISION AUTHORITY

Observe → Assess → Authorize → Act.

The FOC does not bypass mission logic. A command is meaningful only when the relevant state, target information and operational constraints support the requested transition.

CONTROL PHILOSOPHY

Command follows state.

The operational interface is organized around a controlled sequence: establish the mission state, confirm the target, evaluate constraints, authorize the next action and return to observation after the action.

MEASUREMENT → STATE ESTIMATION → CONSTRAINT CHECK → DECISION → COMMAND → RE-OBSERVATION
COMMAND RESULTING STATE OPERATIONAL PURPOSE
HOLD HOLD Inhibit approach while maintaining monitoring.
PROCEED APPROACH Authorize the simulated proximity sequence.
REACQUIRE ASSESSMENT Refresh target state before continuing.
ABORT APPROACH SURVEILLANCE Terminate approach and return to monitored operation.
08 · ENGINEERING MODEL BOUNDARY

What this FOC represents — and what it does not.

REPRESENTED

Mission state, target selection context, relative-navigation visualization, command-state transitions, telemetry presentation, resource indicators and operational event history.

SIMULATED

Orbital relationships, target motion, mission-state behavior, capture authorization and interface telemetry are represented through the project's conceptual simulation model.

OUTSIDE SCOPE

Real spacecraft commanding, flight-qualified navigation, certified collision-avoidance performance, operational ground networks and real-time mission telemetry.

09A · OPERATIONAL GATES

Command authorization gates

The FOC presents a gate-based command philosophy. A requested action is meaningful only after target identity, state information, constraints and mission decision are available. A HOLD decision remains an operational outcome; it is not a failed interface state.

09D · TRACEABILITY CHAIN

From observation to verified interface state

01

OBSERVE

Acquire or load the target record and identify its source.

02

ESTIMATE

Represent position, velocity, risk and prediction horizon.

03

DECIDE

Expose HOLD, PROCEED or ABORT without silently changing the upstream record.

04

COMMAND

Apply only a simulated FOC state transition unless hardware is separately connected.

05

RE-OBSERVE

Return to monitoring and record the resulting model state.

06

VERIFY

Check displayed state, source, constraints and interface response.

07

RECORD

Maintain a readable event and telemetry history for review.

08

BOUNDARY

Clearly distinguish simulation behaviour from flight-qualified operation.
